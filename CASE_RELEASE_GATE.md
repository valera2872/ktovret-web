# Mystery Logic — обязательный Case Release Gate

Статус: **обязательный стандарт проекта**.

Этот документ определяет, когда большое расследование Mystery Logic может считаться готовым к публикации. Он применяется к премиальным кооперативным делам и другим длинным расследованиям, где игрок должен самостоятельно вывести решение из материалов.

## Главный принцип

Авторская проверка «я несколько раз прошёл дело и всё выглядит хорошо» **не считается достаточной**.

Дело может получить статус `READY TO PUBLISH` только после полного Release Gate, выполненного **после заморозки контента** и на той же версии дерева, из которой будет собран production-архив.

Если после начала Gate меняется что-либо, способное повлиять на сюжет, вывод игрока, порядок раскрытия, UX, оплату или игровой цикл, прежний Gate **аннулируется**. Проверка начинается заново. Нельзя переносить PASS со старой версии по принципу «это мы уже проверяли вчера».

## Когда Gate запускается автоматически

Release Gate обязателен без дополнительной команды пользователя:

1. Перед первым выпуском нового большого дела.
2. Перед словами «дело готово», «готово к публикации», «можно заливать на production».
3. После существенной правки уже выпущенного дела, если менялись:
   - вводная, анонс, paywall или предыгровые экраны;
   - материалы, показания, факты, заголовки материалов;
   - этапы, цели этапов, подсказки, feedback;
   - обмены между ролями;
   - варианты ответа, финальная форма, доска доказательств, reveal;
   - порядок загрузки материалов или доступность информации;
   - серверная логика комнат, entitlement, платёжная граница;
   - любые изменения, способные облегчить, усложнить или преждевременно раскрыть решение.
4. После обнаружения игроком или владельцем проекта сюжетного/UX/спойлерного дефекта, даже если исправление кажется локальным.

Косметическая правка, не меняющая смысл, порядок раскрытия, интерактивность или доступность информации, не обязана обнулять Gate. При сомнении считать правку существенной.

## Ручная контрольная команда

Фраза пользователя **«Полный Release Gate»** означает:

- остановить подготовку релиза;
- не доверять предыдущим PASS;
- считать текущую версию новым кандидатом;
- пройти все секции этого документа заново;
- не объявлять дело готовым, пока все обязательные секции не получат PASS.

Эта фраза — аварийная команда. Для обычного релиза пользователь не обязан её произносить: Gate должен запускаться автоматически.

# Последовательность Release Gate

## G0. Content Freeze — PASS/FAIL

До проверки фиксируется кандидат:

- сюжет и решение;
- все материалы обеих ролей;
- обмены и маркеры;
- подсказки;
- UI-тексты;
- финальные вопросы и доказательная доска;
- paywall/анонс/предыгровые экраны;
- backend игровой комнаты и платёжная граница.

После G0 запрещено тихо менять содержимое во время аудита. Любая существенная правка → назад в G0.

## G1. Evidence & Fair-Play Audit — PASS/FAIL

Проверить каждое утверждение финальной версии.

Для каждого вывода должно быть явно установлено:

`материал(ы) до финала -> допустимый вывод -> часть обвинения`

Обязательные вопросы:

- Можно ли доказать виновного без reveal?
- Можно ли отдельно доказать каждое необходимое действие, а не только «он подозрительный»?
- Нет ли факта, впервые появляющегося только в развязке?
- Реалистичны ли время, расстояния, размеры, механика, доступ, цифровые логи, цепочка хранения?
- Не подменяет ли мотив доказательство действия?
- Есть ли минимум две независимые линии там, где одна улика может иметь альтернативное объяснение?

## G2. Adversarial Countertheory Audit — PASS/FAIL

Отдельный проход пытается **оправдать канонического виновного** и построить максимально сильные альтернативы.

Минимум проверить:

- каждого другого основного подозреваемого;
- несчастный случай / совпадение;
- сообщника;
- подставу;
- подделку или ошибку технических логов;
- перенос/подбрасывание физической улики;
- ошибочную идентификацию;
- альтернативное объяснение ключевого временного окна.

Каждая правдоподобная контрверсия должна ломаться независимыми фактами, доступными до финала.

## G3. Blind Spoiler Audit — PASS/FAIL

Это **отдельная проверка**, а не часть G1.

Проверяющий действует как новый игрок, который не знает решения. Проверяется весь путь строго в порядке появления:

1. карточка/анонс в каталоге;
2. paywall;
3. экран после покупки;
4. описание ролей;
5. вводная;
6. названия этапов;
7. цели этапов;
8. заголовки материалов;
9. подписи/facts;
10. обмены между ролями;
11. совместные решения;
12. закрытые и открытые подсказки;
13. feedback после ошибки;
14. финальная форма;
15. названия и подписи доказательств;
16. ожидание второго игрока;
17. reveal — только здесь разрешён полный ответ.

Задача прохода: попытаться **угадать правильную версию как можно раньше** по авторским формулировкам, а не по уликам.

FAIL, если интерфейс:

- формулирует гипотезу вместо игрока;
- советует не доверять конкретному алиби до появления оснований;
- выделяет правильный механизм преступления раньше времени;
- в названии материала сообщает вывод, который игрок должен сделать сам;
- перед финальным вопросом называет виновного или фактически подписывает правильный ответ;
- feedback после ошибки раскрывает недостающий ключ вместо нейтрального направления к материалам.

## G4. Solvability & Difficulty Audit — PASS/FAIL

После удаления спойлеров доказать обратное: дело осталось решаемым.

Для каждого финального ответа составить цепочку:

`A + B (+ C) -> X`

Проверить:

- игроку не требуется авторское знание;
- нужный материал действительно доступен к этому моменту;
- обмен между ролями не требует передачи информации, которой у партнёра нет;
- маркер/код можно получить без угадывания;
- отсутствие подсказки не превращает задачу в перебор;
- optional hints помогают, но не являются обязательными для честного решения.

## G5. First-Time Player UX Audit — PASS/FAIL

Проверка без знания проекта.

В первые 30–60 секунд должно быть понятно:

- что произошло;
- зачем игрок здесь;
- что от него требуется сейчас;
- чем отличаются две роли;
- почему нельзя просто показать друг другу весь экран;
- куда нажимать дальше.

Проверить desktop и mobile. Не допускать перегруженного первого экрана, неизвестных внутренних терминов без объяснения и интерфейса, где игрок вынужден догадываться о механике сайта.

## G6. Black-Box Game Flow — PASS/FAIL

Проходить не данные, а реальный пользовательский цикл.

Обязательно:

- paywall;
- создание комнаты;
- приглашение второго игрока;
- вход гостя бесплатно, если такова модель;
- обе роли;
- каждый этап;
- каждый обязательный handoff;
- неверный маркер;
- правильный маркер;
- открытие подсказки;
- неверный финальный ответ;
- неполная доказательная конструкция;
- правильный ответ;
- ожидание завершения напарника;
- reveal;
- refresh/reload;
- повторный вход по URL комнаты;
- mobile и desktop;
- просроченная/неверная комната там, где применимо.

Визуальный smoke должен начинаться **до первого игрового пакета**, а не с него. Предыгровые экраны входят в игровую поверхность.

## G7. Commerce & Security Boundary — PASS/FAIL

Для платного дела проверить:

- цену на фронте;
- цену на сервере;
- product id;
- checkout endpoint;
- payment-status;
- webhook;
- entitlement;
- создание комнаты без entitlement запрещено сервером;
- приглашённый бесплатный игрок не получает возможность создавать оплаченные комнаты;
- прямой API-вызов не обходит оплату;
- платёж другого продукта не открывает это дело;
- refund/revoke не оставляет активный доступ, если эта логика предусмотрена.

Нельзя считать фронтовый paywall защитой покупки.

## G8. Regression Audit — PASS/FAIL

Новое дело не должно ломать существующие продукты.

Минимум для текущей архитектуры Mystery Logic:

- `23:17`;
- `Номер 407`;
- первый том / 99 ₽;
- бесплатные 15 дел;
- каталог;
- SEO-маршруты и sitemap;
- legal/footer;
- общая статистика/аналитика;
- production web build.

## G9. Production Artifact Audit — PASS/FAIL

Последняя проверка выполняется **не на рабочем дереве**, а на том артефакте, который реально будет передан на hosting.

Для ZIP:

- распаковать в чистую директорию;
- проверить структуру корня;
- убедиться, что нет dev/private файлов;
- проверить обязательные страницы и ассеты;
- проверить финальные cache keys/версии;
- повторить критический spoiler/commerce/game-flow smoke на содержимом ZIP;
- убедиться, что ZIP соответствует прошедшему Gate commit/tree.

Только после G9 разрешена формулировка `READY TO PUBLISH`.

# Независимые роли проверки

Один проход не должен пытаться решить всё сразу. Для каждого релиз-кандидата выполняются конфликтующие роли:

1. **Следователь** — доказывает каноническую версию.
2. **Адвокат** — пытается оправдать канонического виновного.
3. **Спойлер-хантер** — пытается угадать ответ раньше времени по UI и формулировкам.
4. **Застрявший игрок** — ищет место, где честный игрок не может сделать следующий вывод.
5. **QA/абьюзер** — ломает порядок экранов, комнату, refresh, оплату и прямые API-границы.
6. **Новый пользователь** — оценивает первые 30–60 секунд без знания внутренней терминологии проекта.

Нельзя заменять эти роли формулировкой «ещё раз внимательно прошёл дело».

# Правило статуса

Допустим только такой итоговый отчёт:

- G0 Content Freeze — PASS
- G1 Evidence/Fair Play — PASS
- G2 Countertheories — PASS
- G3 Blind Spoiler — PASS
- G4 Solvability/Difficulty — PASS
- G5 First-Time UX — PASS
- G6 Black-Box Flow — PASS
- G7 Commerce/Security — PASS
- G8 Regression — PASS
- G9 Production Artifact — PASS

Если хотя бы один пункт `FAIL`, `UNKNOWN`, `NOT RUN` или относится к предыдущей версии, статус дела — **NOT READY**.

# Что должен видеть владелец проекта

Пользователь не обязан лично проходить дело для поиска логических дыр, спойлеров или технических обходов.

Перед публикацией ему достаточно получить короткий отчёт:

`Release Gate: 10/10 PASS · audited tree <sha> · production artifact <digest>`

и перечень обнаруженных/исправленных дефектов, если они были.

Личная игра владельца остаётся продуктовой оценкой вкуса, атмосферы и коммерческого впечатления, а не обязательным QA-этапом.
